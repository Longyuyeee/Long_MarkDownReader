# G8-2A 文件关系上下文侧栏审计

审计日期：2026-07-26

开发分支：`codex/a4-format-closure`

对应目标：用户不离开当前文件工作面，也能理解关系对象、方向、类型和来源证据

## 1. 目的对齐

G8-1 解决“关系是否存在”的可见性，G8-2A 继续解决“关系是什么、为什么成立、能否直接打开”的解释问题。本批不创建第二套图谱，也不把完整图谱画布嵌入每个编辑器，而是在应用壳层提供统一、可折叠的只读关系抽屉。

本批退出条件：

- 当前文件工作面始终有统一的“关系上下文”入口；
- 关系区分事实、结构、规划和语义类别；
- 有原文依据的关系显示上下文、行号和语法；
- 关系对象可直接定位到 Markdown、PDF 批注、Table 视图、Canvas 节点或 OPML 主题；
- 可以从侧栏进入以当前文件为中心的图谱；
- 尚无提取器的开发/配置格式明确显示能力边界，不伪造零关系；
- 单次最多返回 80 条关系，避免无限制渲染。

## 2. 实现与边界

### 2.1 统一后端合同

新增 `get_graph_relation_context`，返回：

- 当前文件图谱节点；
- 来源对象、目标对象和定位信息；
- 入链、出链、文件内部或双向方向；
- `fact`、`structure`、`planning`、`semantic` 分类；
- 最多三条原文证据；
- 是否进入索引、是否因 80 条上限被截断。

工作区守卫先校验目标必须是知识库内现存文件。命令只读取现有图谱事实源，不修改用户文件，也不执行代码或配置。

### 2.2 共享应用侧栏

新增 `FileRelationContext.vue` 并挂载在应用工作区壳层，而不是分别复制到编辑器中。当前覆盖：

- Library 内的 Markdown 和日常文本/代码/配置编辑器；
- PDF；
- Table；
- Canvas；
- OPML 思维导图。

侧栏保持展开状态，文件切换时自动刷新；首次从无文件页面进入文件工作面也会立即加载。

### 2.3 诚实的能力表达

Markdown、PDF、Table、Canvas 和 OPML 已有图谱提取器，可以显示事实或结构关系。普通代码、JSON、YAML、XML、TOML 等格式当前仍显示“尚未提取这种格式的关系”，继续正常管理和编辑；其 import、相对路径和配置键关系留到 G8-4，不将文件存在误报为孤立事实。

## 3. 审计中发现并修复的问题

1. 首次真实桌面审计发现，从 Library 切入独立 OPML 工作面后自动化未恢复展开抽屉。
2. 第二轮确认抽屉入口存在，但首次挂载没有触发数据加载。
3. 根因是组件只监听后续路径变化，没有在已经展开且首次挂载时立即执行请求。
4. 修复为路径监听 `immediate: true`，第三轮真实 Tauri 审计通过。

该问题说明应用级共享组件必须同时覆盖“同组件切换路径”和“组件首次出现”两个生命周期。

## 4. 验收证据

机器合同 `npm run check:graph-product-contract` 校验有界请求、类型、证据、分类、未提取状态、路由覆盖和居中导航。

Rust 新增两项语义测试：

- 事实、结构/规划分类、方向及证据；
- 尚未提取格式返回安全的未索引状态。

A5/G8 联合真实桌面门禁现为 **24/24 项检查、16 张真实 Tauri WebView2 截图**。本批新增：

- `g8-file-relation-context.jpg`：Markdown 事实关系、目标对象、原文与行号；
- `g8-opml-planning-context.jpg`：OPML 文件与主题层级的规划关系。

## 5. 未完成范围

- 同标签文件的显式共现关系；
- 大型知识库的持久化关系上下文缓存与增量失效；
- 代码 import、配置键、数据路径等 G8-4 提取器；
- 在搜索结果中解释“为什么相关”；
- 在侧栏直接编辑或批准关系。
