v1.0.0 已达到“日常管理 + 基础编辑 + 成体系组织”的初始产品目标，并已通过本地完整质量门禁。项目所有者明确决定本次发布不要求 Authenticode 代码签名，因此历史 R5N 商业签名门禁不再阻止社区版；未知发布者提示、官方来源和 SHA-256 核验必须持续披露。

## 发布证据

正式发布的 NSIS 必须与 GitHub 运行 `30707592201` 测试的字节完全一致：SHA-256 为 `6dae10b828424d0b03ddd4b4b759bcbae94fcbeca4cd37b6da26edc9f2802ee6`，来源提交为 `6f3ce5053bce430803bee9722678ae911aa06d79`。R5K 导入器已重新验证固定成员集、成员摘要、源码提交、安装包摘要、隐私边界和测试结果。

托管环境完成 18 项生命周期检查和 12 项安装后检查。安装后 TXT/JSON 标记可见、对比度 16.41:1、位于文件库右侧工作区；知识网络、指导入口、回执复核、11 个代表路由、管理备份恢复和索引重建均通过。

## 更新与密钥边界

应用使用 Tauri 更新插件，每 24 小时最多自动检查一次，并提供手动检查、下载、安装和重启。`latest.json` 与安装包 `.sig` 随 Release 发布；客户端以仓库配置的公钥验证更新。私钥和密码只保存在被 `.gitignore` 排除的 `.release-secrets/`，不会提交或上传。

换电脑继续发布维护时，应通过可信的离线或端到端加密渠道单独迁移更新私钥；仅克隆 GitHub 仓库无法签发后续自动更新。

## 已知限制

- Windows 可能显示未知发布者或 SmartScreen 提示。
- 托管生命周期环境是 Windows Server 2025，不宣称已经完成独立 Windows 10/11 客户端认证。
- “有限验证”和“外部依赖”格式继续受能力矩阵约束，不能被宣传成全量无损编辑。
- 自动更新完整性签名证明更新来自持钥发布者，但不提供 Windows Authenticode 发布者身份。

## 发布顺序

1. 完整 `ci:check` 通过，并记录远程 Quality Gate。
2. 生成 ASCII 文件名的 NSIS、MSI、对应 `.sig`、`latest.json` 和 `SHA256SUMS.txt`。
3. 将发布分支快进到 `main`，在最终发布提交创建 `v1.0.0` 标签。
4. 创建 GitHub Release，上传全部资产，核对下载摘要和 `latest.json` 地址。
5. 发布后更新 `shared/v1-community-release-policy.json` 的发布状态，不移动标签。
