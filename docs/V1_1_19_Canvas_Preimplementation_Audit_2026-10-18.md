# v1.1.19 画布与脑图：实施前代码审计与接续

本记录承接 v1.1.18；这是下一版的实施前审计，不是已经完成的功能或验收。当前批次只收尾 PPTX，不能因为发现下一版问题就扩大本次封板范围。方向仍是深化现有基础功能，不新起协作平台，也不把已有多选、撤销或文件卡片包装成新增能力。

## 用户要完成的任务

“把几个资料和想法放到一张图里，拖动整理、修改文字，保存后重开；需要原资料时能准确回去。取消或失败时，我刚写的内容和别人改过的文件都不能丢。”

原路线见 [基础能力深化路线](Foundation_Deepening_Roadmap_1_1_8_to_1_1_20_2026-10-17.md)。JSON Canvas、OPML、外部文件显式授权和显式保存继续保留；格式转换不能假称无损。

## 已读实际代码与现有能力

- `src/views/CanvasView.vue`：文本/文件/链接/分组、图表和 Mermaid 引用；选择、框选、复制剪切粘贴、对齐分布、吸附、连线属性、分支折叠/整理、手工位置恢复、撤销重做、视口裁剪和显式保存均已存在。拖动与双击打开来源已有区分。
- `src/views/MindMapView.vue`：树形大纲/脑图、多选拖动、主题编辑、层级操作、四种布局、撤销重做、折叠、位置记忆和 OPML→Canvas 投影均已存在。投影前已有具体损失说明，不再增加用户必须手工执行的“格式审计”步骤。
- `src-tauri/src/commands/canvas.rs`、`mindmap.rs`：工作区边界、文档租约、可靠写入、外部授权与外部签名保护已存在。OPML 库内写入也有预期签名校验；不能误称所有保存都没有冲突保护。
- `src-tauri/src/formats/canvas.rs`、`opml.rs`：Canvas 校验及开放 JSON、OPML 属性/备注/头部元数据和坐标序列化、OPML→Canvas 映射已有实现。
- `src-tauri/src/commands/files.rs`、`file_management.rs`、`src/services/fileNavigation.ts`：重命名/移动与托管文件导航是已有流程；引用接续必须复用这些身份与边界机制，不能仅凭同名文件猜测来源。

## 代码可见的优先风险（尚待真实页面复现）

1. **P1，库内 Canvas 并发覆盖。** `read_canvas_file` 返回的 `FileContent` 不含签名，`write_canvas_file` 只有 root/path/content，没有 expectedSignature；租约能串行化当前写入，但不等于防止读取后他人修改被覆盖。下一版优先补库内读写快照及旧命令兼容边界，真实磁盘验证拒绝冲突且保留草稿。
2. **P1，同组件切换/迟到读取。** Canvas 监听 path/external/node 后直接 `loadCanvas`，仅注册 route-leave、没有 route-update 草稿门禁；两页读取回调都未见文件归属/请求世代校验。OPML 的 route-update 已保护不同文件，不能说完全缺失；但同文件定位参数触发 load 仍需核对是否重新读盘抹掉草稿。需要延迟 A→B、同文件定位、切库与返回的真实组件失败用例，再修改。
3. **P1，保存中继续输入。** Canvas 保存成功直接标 saved/清当前 tab dirty，OPML 保存成功直接以返回 document 替换当前 document 并清 dirty；未见快照世代绑定。必须验证“点保存后继续输入”“保存未完成切换”的结果归属，不能用禁掉全部编辑、自动代存或清草稿来制造通过。
4. **P1/P2，来源路径语义。** Canvas `resolveFilePath` 对相对 file 值按当前画布父目录拼接；OPML 投影源卡片写的是相对资料库根的路径。子目录投影存在重复拼接风险。需要跨目录中文样例实证，并统一开放格式的相对路径语义。改名/移动后的身份接续尚未证明，不能宣传已支持。失效卡片应说明原因并允许重新指定来源，绝不自动打开猜测的同名文件。
5. **P2，格式与编辑保真边界。** Canvas 保留额外 JSON 字段已有代码；OPML 会规范化为 2.0 XML，且序列化跳过某些不支持的 head 名称。需要用未知字段、命名空间、备注、折叠及中文的外部样例核对真实往返，保真做不到时在写入前具体说明或阻止有损覆盖，不只依赖旧的通用说明。
6. **P2，直接操作与密集图。** 已有拖动阈值、文字编辑和多选；下一版先在正常动效及六风格/深浅、窄宽页面实测误开、编辑焦点、撤销粒度、分组移动与密集节点可读性，不无证据重写整个画布引擎。

以上为静态代码风险，不冒充本机或安装包已复现的缺陷。实施后逐项补“原失败→修复→真实组件→原生磁盘/固定安装包”证据。

## 分批推进与验收

1. 先做最小失败复现与修改前示意，展示保留所有入口后的直接操作/来源状态；实际查看页面后再动 UI。
2. 先收口归属、保存快照、切换和库内 Canvas 冲突保护；覆盖取消、读写失败、迟到回包、其他窗口修改及连续输入。原件、草稿与他人版本三者分别验证。
3. 统一文件卡片路径/身份与失效反馈，再验证跨目录、重命名、移动、外部授权；没有安全来源时不越权读取。
4. 深化已有选择、对齐、分组、文字编辑和撤销粒度；只改真实用户痛点，保留全部工具、开放格式和正常动效。
5. 核对 Canvas/OPML 往返和投影损失，保存后重开；密集图、中文及外部真实样例分层记录。必须列出不支持而会丢失的内容，不能删掉这些样例让测试变绿。
6. 本机完整质量/Rust、实际页面检查、固定 MSI/NSIS、全部历版回归与独立同包复验、封板 main CI、原包发布/公开回下载、README 末尾与 Release/交接一致、最终 main/tag CI 均通过才发布。

每批审计与推送后直接推进下一批。v1.1.20 仍是现有 JSON/JSONC、YAML、XML、TOML 的可信修改收口，不是“所有功能做完”；当前十三版路线结束后，再按用户要求审计和规划至少十个后续版本。
