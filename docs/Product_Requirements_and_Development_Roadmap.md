## 1. 文档目的

本文件用于统一产品目标、功能范围、优先级、开发顺序和验收标准，解决以下问题：

- 功能开发缺少统一主线，容易在图谱、Canvas、PDF、Excel 等方向之间跳转。
- 已完成能力与待完成能力没有明确边界。
- “支持某种格式”缺少可验证的产品定义。
- 需求、技术方案、测试和版本验收无法相互追踪。

后续每项开发必须关联一个需求编号；没有进入本 PRD 的功能默认不进入当前版本。

## 2. 用户需求对齐

### 2.1 用户原始目标

| 原始目标 | 对齐后的产品要求 |
|---|---|
| 修复项目现有问题 | 建立安全、稳定、测试、性能和架构基线，不以新增功能掩盖基础缺陷 |
| 增强知识图谱存在感 | 图谱进入编辑器侧栏、搜索、导航、整理和内容生产流程，而非独立展示页 |
| 实现真正的思维导图 | 支持从 Markdown/图谱生成、自由编辑、连接、分组、撤销、多选和开放格式保存 |
| 支持图表、思维导图、Excel、PDF | 通过统一格式适配器接入；不同格式拥有明确的阅读、编辑、批注和索引等级 |
| 完整 Excel 等价编辑器 | 建设原生工作簿编辑工作面，覆盖公式、格式、图表、数据透视、验证、打印与可靠 XLSX 往返 |
| 新的文件格式编辑器 | 先进入统一格式注册、权限、打开路由和可靠写入框架，再按独立工作面逐项实现 |
| 更多主题预设 | 扩展可复用主题 token 和预设，并覆盖所有编辑工作面与深浅模式 |
| 做成专业管理系统 | 形成文档、关系、画布、数据、资料、搜索和仪表盘组成的统一工作台 |
| 审计类似产品并输出设计 | 竞品结论进入产品取舍和验收标准，不直接复制功能数量 |

### 2.2 对齐后的产品定位

> LongEdit 是一个以本地文件为可信数据源，以知识图谱为关系中枢，以开放画布为思考界面，以 PDF 和结构化数据为专业资料管理能力的本地优先知识工作台。

LongEdit 不再仅定位为 Markdown 编辑器。电子表格方向以完整 Excel 等价编辑能力为长期产品目标，但通过独立工作簿内核和渐进验收实现，不把整个 Office 套件的复刻混入同一里程碑。

### 2.3 核心价值顺序

1. 用户数据安全、透明、可迁移。
2. 用户能发现内容之间的关系。
3. 用户能用思维导图和 Canvas 主动整理关系。
4. PDF、表格、图表等资料进入同一搜索和关系网络。
5. 系统能支持长期、规模化的专业资料管理。

## 3. 成功标准

### 3.1 产品成功标准

- 从任意 Markdown 笔记不超过 1 次操作即可看到局部关系。
- 从 Markdown 或图谱不超过 2 次操作即可生成可编辑思维导图。
- Markdown、Canvas、PDF 批注和结构化数据均可被统一搜索和引用。
- 用户文件无需 LongEdit 也能被其他通用工具读取。
- 关键写入操作发生崩溃时不丢失已确认保存的内容。
- 10,000 文件知识库仍能完成增量索引和交互式搜索。

### 3.2 当前阶段不作为成功标准

- 多人实时协作。
- Word/PowerPoint 的完整 Office 排版兼容；这不降低电子表格工作面的 Excel 等价目标。
- 直接修改 PDF 原始页面内容。
- 云端数据库成为唯一数据源。
- 用 AI 自动生成不可解释、不可编辑的结果。

## 4. 目标用户与核心场景

### 4.1 目标用户

| 用户类型 | 主要任务 | 核心痛点 |
|---|---|---|
| 个人知识工作者 | 写作、研究、建立长期知识库 | 内容越来越多，但关系难以发现和维护 |
| 项目/产品经理 | 管理需求、会议、计划、图表和资料 | 文档、表格、脑图分散在不同软件 |
| 研究人员/学生 | 阅读 PDF、摘录、引用和组织主题 | PDF 批注无法进入笔记关系网络 |
| 技术用户 | Markdown、Git、代码和技术文档 | 希望本地可控、可版本化、可扩展 |

### 4.2 关键用户旅程

#### 场景 A：从笔记发现关系

打开笔记 → 右侧看到局部图谱 → 查看关系来源与上下文 → 打开相关笔记 → 修复断链或补充关系。

#### 场景 B：从内容形成思维导图

编辑 Markdown 标题/列表 → 点击“转脑图” → 自动生成层级 Canvas → 多选、拖拽、连线、分组 → 保存为 `.canvas`。

#### 场景 C：从图谱开展主题研究

在全局图谱选择主题 → 展开局部子图 → 发送到 Canvas → 添加网页、PDF、笔记和观点卡片 → 形成专题工作区。

#### 场景 D：PDF 研究

打开 PDF → 搜索和定位 → 高亮或区域批注 → 在 Markdown 中引用批注 → 图谱显示“笔记引用 PDF 批注”的关系。

#### 场景 E：数据管理与图表

打开 CSV/表格 → 编辑、筛选和排序 → 切换为图表或看板 → 把图表嵌入 Markdown/Canvas → 数据源保持唯一。

## 5. 范围和优先级规则

### 5.1 优先级定义

| 等级 | 定义 | 处理原则 |
|---|---|---|
| P0 | 安全、数据完整性、架构阻塞项 | 未完成前不得扩大高风险格式写入范围 |
| P1 | 产品核心差异化能力 | 当前主版本必须完成 |
| P2 | 专业工作流能力 | 基础对象和索引稳定后实施 |
| P3 | 增强与生态能力 | 不阻塞 1.0，可按验证结果排期 |

### 5.2 状态定义

- **已完成**：代码、测试和桌面构建均通过。
- **部分完成**：主流程可用，但仍缺少需求中明确的验收项。
- **未开始**：尚无可验收实现。
- **验证中**：已有技术原型，尚未确认产品或许可可行性。

## 7. 非功能需求

### 7.1 数据安全

- 用户文件是事实源，索引、缩略图和布局缓存必须可删除、可重建。
- 所有写操作必须有明确授权根目录、格式白名单和大小限制。
- PDF 默认只读，批注使用 sidecar 文件。
- 任何自动转换都生成新文件，不静默覆盖源文件。
- 不在日志、配置或错误信息中输出密钥和完整敏感内容。

### 7.2 性能

| 指标 | 目标 |
|---|---:|
| 10,000 Markdown 文件首次索引 | < 30 秒 |
| 单文件增量索引 | < 300 ms |
| 全文搜索首屏 | < 150 ms |
| 2,000 节点全局图谱 | ≥ 45 FPS |
| 1,000 节点 Canvas 基础操作 | ≥ 45 FPS |
| 100 MB PDF 首屏 | < 2 秒 |
| 50,000 行 CSV 首屏 | < 2 秒 |

### 7.3 兼容性与可迁移性

- Markdown 保持 CommonMark/GFM 友好。
- Canvas 遵循 JSON Canvas 1.0，未知字段往返保留。
- 表格至少支持 CSV/TSV 导入导出。
- 批注 sidecar 使用版本化 JSON Schema。
- 新格式必须提供版本号、迁移策略和降级读取方案。

### 7.4 可用性

## 12. 需求变更流程

1. 新需求先说明目标用户、场景和解决的问题。
2. 评估是否属于现有需求；属于则更新验收标准，不重复立项。
3. 不属于时分配新编号、优先级和目标里程碑。
4. 涉及数据格式、写入、安全或依赖许可时必须先完成技术审计。
5. 开发完成后更新状态、测试证据和已知限制。
6. 未满足验收标准的功能只能标记“部分完成”，不能标记“已完成”。

## 13. 关键产品决策

| 决策 | 结论 |
|---|---|
| 数据事实源 | 用户文件，不是内部数据库 |
| 图谱与 Canvas 的关系 | 图谱负责发现，Canvas 负责表达和整理 |
| 思维导图格式 | 层级事实源使用开放 OPML 2.0，自由空间投影使用 JSON Canvas；不建立封闭专有格式 |
| PDF 编辑范围 | 阅读和批注，不承诺原始排版编辑 |
| Excel 实施顺序 | 保留 CSV/Table 基线，下一主线建设完整工作簿内核与分层 XLSX 往返 |
| 图表保存方式 | 保存可编辑源码或配置，不以图片作为唯一源 |
| 索引定位 | 可重建缓存，不是唯一事实源 |
| AI 定位 | 辅助生成、提取和整理，结果必须可编辑和可追踪 |
| 1.0 协作范围 | 本地单用户优先，实时协作不进入 1.0 主线 |
