# R1 统一发布能力矩阵审计

日期：2026-07-30
阶段：R1
结论：39 类已注册格式已全部进入同一份机器可读发布矩阵，并在设置中提供可搜索、可筛选的产品查询入口。当前仍为基础版本收口阶段，不标记发布候选。

## 1. 本步改善的用户任务

用户现在可以从“设置 → 格式能力”直接确认某种格式是否可编辑、如何保存、是否依赖外部应用、源文件会不会被修改，以及当前已知限制，不再需要阅读开发审计文档猜测真实能力。

## 2. 统一事实源

- `shared/file-formats.json` 继续负责格式、扩展名、读写创建索引能力和公开能力等级。
- `shared/release-capability-matrix.json` 负责发布阶段、应用版本、依赖、源文件策略、隐私边界、已知限制与外部门禁。
- 两份事实源通过格式 ID 关联，不重复维护读写能力字段。
- R1 契约要求 39 个注册格式恰好映射一次，禁止缺失、重复、未知策略或外部依赖降级描述。

当前统计：

| 状态 | 数量 | 含义 |
| --- | ---: | --- |
| `verified` | 27 | 已验证本地工作流 |
| `verified-with-limitations` | 6 | 已验证有限能力，界面必须展示边界 |
| `external-dependency` | 6 | 依赖兼容 Office 或桌面应用 |

矩阵共使用 10 个发布策略档案，覆盖本地可靠保存、敏感文件保护、轻量源码、只读日志、PDF sidecar、Office 新副本、ODF 预览、旧格式隔离转换、WPS 外部打开和 XLSX 有限写回。

## 3. 产品入口

- 新增 `/release-capabilities` 工作面。
- 支持按格式名、格式 ID 和扩展名搜索。
- 支持“全部 / 已验证 / 有限能力 / 外部依赖”分段筛选。
- 每行直接显示公开能力、保存边界和依赖；展开后显示源文件策略、隐私边界、已知限制和注册表能力说明。
- 设置页“系统集成”增加“格式能力”入口。
- 桌面与窄屏均使用稳定网格；窄屏隐藏次要列，并保留能力与展开详情。

## 4. 不夸大的边界

- `releaseCandidate` 保持 `false`。
- E1B WPS ODT 保持 `partial 2/3`，`.odt` 仍未注册。
- X3-B6 数组生产者保持 `partial 1/3`，数组计算与写回仍阻断。
- 旧 DOC/XLS/PPT 的转换能力明确依赖兼容 Office 应用。
- WPS 原生格式明确只做身份预检和外部打开。
- 本批没有完成真实 Tauri 明暗主题与紧凑窗口截图，因此不宣称桌面视觉矩阵关闭；该项进入 R2。

## 5. 门禁

- `npm.cmd run check:r1-release-capability-matrix`：通过，39 格式、10 策略档案。
- `npm.cmd run build`：通过，`vue-tsc --noEmit` 与 Vite 生产构建均成功。
- R1 契约已接入 `check:format-contract`，因此进入共享 `ci:check`。
- GitHub Quality Gate 继续固定 Node.js 22。`actions/setup-node@v6` 升级因当前推送凭据缺少 workflow 修改权限而转入 R2 仓库维护项，不影响 R1 产品能力验收。
- 本机 `npm.cmd run ci:check` 已通过构建、全部契约链和 Rust 功能测试（`406 passed; 2 ignored; 1 filtered out`），但既有 XLSX 性能门禁两次采样的 page/patch 阶段为 `9242/8053ms` 与 `7778/7983ms`，超过发布阈值后退出；阈值未放宽，最终由推送后的 GitHub Quality Gate 干净环境复核。
- 中断后独立补跑 `benchmark:pdf-range`：100 MiB 文件 `637ms`，请求约 `255.9 KiB`；`audit:prod` 为 `0 vulnerabilities`，`cargo check --locked` 通过。
