# LongEdit 后续开发步骤与执行指导

> 文档类型：可执行开发指导
> 版本：1.0
> 更新日期：2026-07-24
> 上位需求：[统一文件管理、阅读与编辑需求基线](./Unified_File_Manager_Format_Requirements.md)
> 主 PRD：[产品需求与开发路线图](./Product_Requirements_and_Development_Roadmap.md)

## 1. 指导目标

本文档把“覆盖日常管理和基础编辑，并把内容进行成体系管理”的基础需求拆成可连续交付的开发步骤。后续开发不再按单一技术模块无限深入，而是按用户可以完成的完整任务闭环推进：

```mermaid
flowchart LR
  A["发现并识别文件"] --> B["应用内阅读"]
  B --> C["完成基础编辑或批注"]
  C --> D["安全保存并重开"]
  D --> E["搜索、分类与再次定位"]
  E --> F["加入集合、引用或关系"]
  F --> A
```

一个阶段只有同时打通识别、打开、使用、保存、搜索和再次定位，才算形成产品交付。仅完成解析器、模型、内存预览或格式登记，不得标记阶段完成。

## 2. 全程执行原则

### 2.1 产品优先级

1. P0：数据安全、原文件不损坏、外部冲突不丢失。
2. P1：日常格式覆盖、阅读体验、基础编辑、可靠保存。
3. P1：统一文件管理、全文搜索、集合和再次定位。
4. P2：格式内部的专业增强能力。
5. P3：高级 Office 等价、自动化和 AI 增强。

在阶段 A～C 完成前，Excel Pivot、高级图表对象和其他单格式深层能力只处理缺陷与数据安全问题，不继续作为唯一开发主线。

### 2.2 垂直切片

每个格式按以下顺序开发：

1. 真实格式与许可证审计。
2. 在共享注册表中声明 `planned`。
3. 完成文件识别、大小限制、外部授权和错误降级。
4. 完成只读解析、预览和真实 fixture。
5. 接入搜索、最近文件和统一打开。
6. 完成受限编辑、可靠保存、冲突检测和语义重读。
7. 达到全部门禁后才把能力改为 `supported`。

禁止先登记为 `supported` 再补实现。

### 2.3 事实源与分层

| 层级 | 当前入口 | 后续职责 |
|---|---|---|
| 共享能力契约 | `shared/file-formats.json` | 扩展名、MIME、大小、路由、能力和适配器事实源 |
| 前端格式消费 | `src/config/fileFormats.ts` | 类型、能力展示、最长扩展名匹配和路由 |
| 前端工作面 | `src/views/` | 阅读、编辑、状态栏和用户交互 |
| Rust 格式层 | `src-tauri/src/formats/` | 解析、序列化、结构验证和保真规则 |
| Rust 命令层 | `src-tauri/src/commands/` | 权限、参数、事务编排和 Tauri 边界 |
| 安全与持久化 | `services/workspace_guard.rs`、`reliable_write.rs` | 路径授权、冲突检测、临时文件和可靠替换 |
| 索引与管理 | `services/knowledge_index.rs`、`commands/search.rs`、`commands/workspace.rs` | 搜索段、对象定位、集合和工作台 |
| 自动化门禁 | `scripts/`、`package.json` | 契约检查、构建、测试、性能和发布审计 |

新业务不得继续堆入 `LibraryMode.vue`、`lib.rs` 或单个巨型命令文件。公共编辑能力放入 composable、组件或服务；格式语义留在独立格式模块。

## 3. 开始开发前的基线步骤

### S0-1：合并并建立干净基线

目标：确保当前文档和已交付能力进入默认分支后再开始新主线。

执行：

1. 审核并合并当前 Draft PR。
2. 在新电脑或新工作树拉取默认分支。
3. 执行 `npm ci` 和 `cargo fetch --locked`。
4. 执行完整 `npm run ci:check`。
5. 记录 Node、Rust、WebView2、Windows 和 Tauri 版本。
6. 不提交 `.claude/settings.local.json` 或机器私有配置。

退出条件：

- 默认分支工作树干净。
- 当前 CI 全绿。
- `shared/file-formats.json` 与前后端契约检查一致。
- 默认分支 `main` 与远端保持一致；后续按当前团队约定直接在 `main` 推进、阶段收尾后提交并推送。

### S0-2：建立三项产品进度指标

在阶段审计中新增：

| 指标 | 计算方式 | 基线要求 |
|---|---|---|
| 日常格式覆盖率 | 已完成“识别+预览”的 P1 格式数 / P1 格式总数 | 不以只登记扩展名计数 |
| 基础编辑完成度 | 已完成“编辑+保存+重开”的 P1 格式数 / 需要编辑的 P1 格式总数 | 部分编辑单独标识 |
| 管理闭环完成度 | 已接入打开、最近、搜索、集合/分类、再次定位的格式数 / 已支持格式数 | 敏感格式可按策略排除搜索 |

每个 Sprint 结束必须更新三项指标、未完成原因和下一阻塞项。

## 4. 阶段 A：统一文本与 JSON 闭环

这是下一开发主线，对应 `FR-TEXT-001～006`、`FR-JSON-001～006`、`FR-DEV-001` 和 `FR-MANAGER-001`。

### A0：格式契约和能力展示升级

目标：先让系统能够准确表达“识别、预览、基础编辑、批注和安全保存”，避免继续用单一 `edit` 布尔语义误导用户。

开发任务：

1. 审计 `shared/file-formats.json` schema v1 的字段是否足以表达预览、批注、导出、保存和敏感索引策略。
2. 如需 schema v2，先为前后端增加兼容解析，再迁移数据，不直接破坏 v1。
3. 前后端文件匹配统一改为“最长扩展名优先”，不能依赖注册表排列顺序。
4. 新增格式能力徽标模型：完整编辑、基础编辑、阅读/批注、仅预览、外部打开、不支持。
5. 文件树、标签页和工作面状态栏消费同一能力模型。
6. 未支持文件仍显示在目录中，并提供外部打开和复制路径。

重点文件：

- `shared/file-formats.json`
- `src/config/fileFormats.ts`
- `src/views/LibraryMode.vue`
- `src/router/index.ts`
- `src-tauri/src/formats/file_registry.rs`
- `src-tauri/src/commands/files.rs`
- `scripts/check-format-contract.mjs`

测试门禁：

- `.table.json` 必须优先于普通 `.json`。
- `.canvas` 使用专用工作面，不能进入通用 JSON 编辑器。
- 大小写扩展名、伪扩展名和扩展名冲突有回归测试。
- `planned` 和 `unsupported` 不能出现可写保存入口。

退出条件：前后端能力声明一致，未知/只读/部分编辑状态可见，最长扩展名匹配不依赖数组顺序。

### A1：可靠文本读取与保存内核

当前风险：现有 `read_text_document` 能检测编码，但 `write_text_document` 始终调用 `write_utf8`。直接扩展更多文本格式会导致原编码、BOM 和换行符策略丢失。

目标：建立所有开发文本格式可复用的无损基础。

开发任务：

1. 新增 `TextDocumentSnapshot`：
   - 规范路径。
   - 内容签名。
   - 检测到的编码及置信状态。
   - BOM 类型。
   - 主换行符 `LF/CRLF/CR`。
   - 是否有末尾换行。
   - 文件字节数、只读原因和修改时间。
2. 读取时区分“确定编码”“用户需要确认”“二进制/拒绝”。
3. 写入命令必须携带读取签名和保存策略，拒绝静默覆盖外部修改。
4. 保存默认保留原编码、BOM、换行符和末尾换行；转换编码必须是显式命令。
5. 将 `reliable_write.rs` 的可靠替换用于最终字节，写后重新读取并验证。
6. NUL、损坏编码、超限文件和只读权限返回结构化错误。
7. 大文件增加按字节范围读取接口；超过编辑阈值默认进入渐进只读模式。

建议模块：

- 新增 `src-tauri/src/formats/text.rs`
- 扩展 `src-tauri/src/commands/formats.rs`
- 新增 `src/types/textDocument.ts`
- 新增 `src/composables/useTextDocument.ts`

真实 fixture：

- UTF-8、UTF-8 BOM、GB18030/GBK 可判定样本。
- LF、CRLF、混合换行、无末尾换行。
- 空文件、大文件、NUL 文件、无效字节序列。
- 外部修改、写入中断和只读文件。

退出条件：打开、编辑、保存、重开后编码与换行策略符合用户选择；外部冲突不会被覆盖；失败不会损坏源文件。

### A2：统一文本工作面

目标：让 TXT 先形成完整日常编辑体验，再复用到日志、配置和代码。

开发任务：

1. 新建独立 `TextEditorView.vue`，不要继续复用 Markdown 专属工作面。
2. 编辑器选型先完成 ADR，至少比较：
   - 包体积和首次加载。
   - 大文件能力。
   - 许可证。
   - 查找替换、行号、语法高亮和只读范围。
   - Vue 3 与 Tauri WebView2 稳定性。
3. 首版交互：
   - 行号、当前行列。
   - 编码、BOM、换行符和文件大小。
   - 查找替换、大小写、整词、正则和跳转到行。
   - 撤销重做、未保存提示、重新加载和另存为。
   - 外部冲突对话框。
4. 大文件工作面：
   - 默认只读。
   - 分块读取和搜索。
   - 明确提示为何不能直接编辑。
5. 标签页关闭、切换工作区和应用退出时统一处理未保存内容。

退出条件：TXT 从文件树、系统打开、最近文件和搜索结果进入同一工作面；保存、关闭、重开流程通过真实桌面验收。

### A3：普通 JSON 与 JSONC

目标：提供面向开发与配置管理的通用 JSON 工作面，同时保护专用 JSON 格式。

开发任务：

1. 在注册表中新增普通 `.json` 和 `.jsonc`，状态先设为 `planned`。
2. 新建 `JsonEditorView.vue`，包含源码与树形双视图。
3. 文本内容是第一阶段事实源；不得用普通对象序列化覆盖用户原始格式。
4. JSON 源码视图：
   - 语法错误位置。
   - 重复键提示。
   - 格式化和压缩。
   - 折叠、搜索和 JSON Path。
5. 树形视图：
   - 对象、数组和标量增删改。
   - 节点复制、路径复制和类型修改。
   - 大整数和高精度数字不得经 JavaScript `number` 静默失真。
6. JSONC：
   - 注释必须保留。
   - 未引入可保留注释的语法树实现前，只开放源码编辑，不开放会重排全文的结构化写回。
7. 非法 JSON 可以保留为未保存草稿；覆盖原文件必须经过明确的“按纯文本保存”确认。
8. 索引提取字段名、字符串值和受限标量，避免把标点结构噪声写入索引。

重点测试：

- `.table.json`、`.canvas` 与普通 `.json` 路由。
- 空对象、深层对象、超大数组、Unicode 键、重复键。
- 大整数、小数、指数、负零。
- JSONC 行/块注释和尾逗号。
- 损坏 JSON 的草稿恢复和原文件保护。

退出条件：普通 JSON 可识别、阅读、校验、搜索、基础编辑、安全保存和重开；JSONC 未验证的结构化编辑保持禁用。

### A4：日志、YAML、XML、TOML 和配置格式

目标：利用统一文本内核扩展日常开发文件覆盖，不把它们误宣称为完整 IDE。

开发顺序：

1. `.log`：自动刷新、筛选、时间/级别高亮、默认只读。
2. `.yaml/.yml`：源码编辑、语法校验和结构大纲。
3. `.xml`：源码编辑、折叠、格式化和树形只读预览。
4. `.toml/.ini/.conf/.properties`：语法高亮、键值搜索和编辑。
5. 常见代码扩展：先识别、阅读、语法高亮和搜索，再开放轻量编辑。

敏感文件规则：

- `.env` 默认遮罩值。
- `.env`、密钥和凭据疑似文件默认不进入索引、图谱、日志和遥测。
- 用户解除遮罩和允许索引必须分开授权。
- 任何代码执行、脚本运行和依赖安装均不属于本阶段。

退出条件：各格式均有真实 fixture、正确路由和降级状态；新增扩展不破坏现有格式；敏感文件默认保护。

### A5：阶段 A 桌面验收

必须在真实 Tauri 桌面完成以下路径：

1. 从文件树打开 TXT/JSON。
2. 从 Windows 文件关联或拖拽打开。
3. 编辑并保存。
4. 使用外部程序修改同一文件，验证冲突处理。
5. 重启应用并从最近文件再次打开。
6. 全文搜索定位到行号或 JSON Path。
7. 加入收藏或智能集合。
8. 验证 `.env` 不进入搜索。
9. 验证大文件进入只读降级。
10. 验证损坏 JSON 不覆盖最后合法版本。

阶段 A 完成后，更新注册表能力、主 PRD、格式需求矩阵、开发审计和发布说明。

## 5. 阶段 B：PDF 实用页面编辑

对应 `FR-PDF-008～011`。目标不是立即实现 Acrobat 级正文排版，而是覆盖日常最常用、风险可控的页面整理。

### B0：PDF 写入技术与许可证审计

开发前必须输出 ADR：

- 候选库的许可证、维护状态和安全记录。
- 加密 PDF、数字签名、表单、附件和增量更新能力。
- 合并、拆分、旋转、重排、删除和插入的保真程度。
- Windows 包体积、性能和离线能力。
- 损坏 PDF、对象流、交叉引用表和超大文件处理。

停止条件：

- 无法可靠保留未知对象。
- 写入会静默移除签名、附件、表单或加密信息。
- 许可证不适合项目分发。

触发停止条件时只做“另存副本/外部打开”，不开放覆盖原文件。

### B1：安全事务模型

1. 所有页面操作先生成操作计划，不直接写用户文件。
2. 展示页数变化、源文件、目标文件和签名失效风险。
3. 默认另存为新文件；覆盖源文件需要显式确认。
4. 写入临时副本后执行包解析、页数、页面尺寸和可打开性验证。
5. 验证成功后使用可靠替换。
6. 密码、签名、加密、表单或未知高风险对象默认阻断或降级。

### B2：首批页面操作

按风险从低到高交付：

1. 旋转页面。
2. 提取页面并另存。
3. 页面排序。
4. 删除页面。
5. 拆分 PDF。
6. 合并 PDF。
7. 插入其他 PDF 页面。

每个操作都要覆盖撤销计划、另存、覆盖冲突、重开和索引刷新。

### B3：PDF 管理闭环

- 编辑后的新文件进入最近、搜索和工作台。
- 原批注 sidecar 在页面变化后必须迁移、明确失效或要求用户确认，不能静默错页。
- 缩略图和全文索引按新签名重建。
- 文件关系在另存时提供“继承关系/作为新对象”选择。

阶段 B 退出条件：七项页面操作完成真实 PDF 往返；失败不损坏源文件；批注和页码关系无静默错位。

## 6. 阶段 C：DOCX 与 PPTX 基础工作面

对应 `FR-OFFICE-001～006`。先覆盖日常阅读和基础编辑，不以完整 Office 排版等价为首版目标。

### C0：兼容矩阵和 fixture

建立至少三类生产者样本：

- Microsoft Office。
- WPS Office。
- LibreOffice。

DOCX 样本覆盖段落、标题、列表、表格、图片、分页、页眉页脚、批注、修订和未知扩展。PPTX 样本覆盖文本、图片、基础形状、组合、母版、主题、图表、动画、备注和未知扩展。

每个 fixture 保存：

- 来源和生成步骤。
- 许可证或可再分发说明。
- 预期结构摘要。
- 打开、编辑、保存和重开预期。

### C1：DOCX 只读工作面

1. 基于现有 ZIP 与 XML 安全边界解析 OOXML 包。
2. 读取文档顺序、段落、标题、列表、表格、图片和基础样式。
3. 提供目录、搜索、复制和段落定位。
4. 未支持对象显示占位和说明，不静默消失。
5. 接入索引，搜索结果定位到段落或表格。

### C2：DOCX 基础编辑

首批只开放：

- 普通段落和标题文本。
- 粗体、斜体、下划线、字号和基础颜色。
- 有序/无序列表。
- 简单表格文本。
- 图片替换或插入的受限子集。

写入原则：修改目标 OOXML 部件，其他部件逐字节保留；若目标对象包含未支持的修订、域、复杂绘图或扩展，降级为只读。

### C3：PPTX 只读工作面

1. 幻灯片缩略图和顺序。
2. 基础文本、图片、形状和主题背景预览。
3. 放映模式、页面跳转、备注和搜索。
4. 搜索结果定位到幻灯片和对象。

### C4：PPTX 基础编辑

首批只开放：

- 文本内容及基础字号、颜色和对齐。
- 图片替换。
- 基础矩形、圆形和线条。
- 页面新增、复制、删除和排序。

动画、母版、SmartArt、复杂图表和未知扩展只读保真。不能证明保真的文件不得覆盖原件。

### C5：Office 桌面验收

- 三类生产者 fixture 均完成打开。
- 支持子集完成编辑、保存、重开和原程序复开。
- 未编辑部件执行 ZIP 部件差异门禁。
- 高级对象存在时能力状态和阻断原因清晰。
- DOCX/PPTX 进入最近、搜索、收藏和集合。

阶段 C 完成后，用户应能在 LongEdit 中完成常见 Word/PPT 的阅读、查找和基础修改，但界面仍明确标记“基础编辑”。

## 7. 阶段 D：体系化管理闭环增强

该阶段可以与 A～C 的后半程交错，但不能脱离真实格式独立开发。

### D1：统一文件工作台

- 最近、收藏、未处理批注、最近编辑和常用集合。
- 按格式、能力、目录、标签、日期和状态筛选。
- 清楚显示只读、基础编辑、外部冲突和索引状态。
- 支持批量外部打开、加入集合和重新索引；不默认批量修改原文件。

### D2：统一元数据和分类

- 文件系统目录仍是主要组织方式。
- 标签、收藏和智能集合进入可迁移、可导出的元数据设计。
- 元数据与文件移动/重命名建立稳定迁移规则。
- 不把内部数据库变成唯一事实源。

### D3：跨格式搜索与定位

- TXT/代码定位行号。
- JSON/YAML/XML 定位字段路径。
- PDF 定位页码/批注。
- XLSX 定位 Sheet/单元格。
- DOCX 定位段落。
- PPTX 定位幻灯片/对象。

搜索结果必须显示格式、位置、摘要、所属库和能力状态。

### D4：关系和知识图谱

- 关系创建应来自普通工作流中的“引用、相关文件、附件和来源”，不要求用户先打开全局图谱。
- 文件详情和编辑器侧栏优先展示局部关系。
- 全局图谱负责探索，不承担文件管理的唯一入口。
- 关系断裂、文件移动和路径变化进入健康检查。

阶段 D 退出条件：用户可从工作台发现文件，完成阅读/编辑，保存后通过搜索、集合或关系再次找到它。

## 8. 阶段 E：格式广度

在 A～D 的 P1 闭环稳定后依次推进：

1. SVG 预览与基础编辑。
2. Draw.io 许可、嵌入和往返审计。
3. `.odt/.ods/.odp` 阅读与搜索。
4. `.wps/.et/.dps` 识别、预览或安全转换。
5. `.doc/.xls/.ppt` 外部打开和显式转换。
6. 更广泛的代码格式语法高亮与符号大纲。

每个格式仍执行同一垂直切片，不允许一次性只添加扩展名白名单。

## 9. 阶段 F：长期高级能力

只有基础需求指标达到发布门槛后再排期：

- PDF 正文和排版编辑。
- PDF 表单、敏感信息擦除和签名工作流。
- Excel 高级 Pivot、外部连接和复杂绘图对象。
- DOCX 修订、域、复杂分页和高级排版。
- PPTX 母版、动画、SmartArt 和复杂图表。
- 自动分类、内容抽取和 AI 辅助整理。

AI 产生的标签、关系、摘要和转换结果必须可预览、可编辑、可撤销，并保留来源。

## 11. Definition of Done

需求只有同时满足以下条件才能标记“已完成”：

- 有明确需求编号和用户路径。
- 真实文件可识别并进入正确工作面。
- 支持的阅读内容通过 fixture 验证。
- 支持的编辑操作可撤销或有明确恢复路径。
- 保存使用可靠写入并检测外部冲突。
- 保存后可由 LongEdit 重开。
- 交换格式可由至少一个目标第三方程序重开。
- 未支持对象不丢失，或保存前明确阻断。
- 文件进入最近记录、搜索和统一管理入口。
- 错误提示可理解且不泄露敏感内容。
- 前后端测试、契约检查和构建通过。
- 文档中的状态和限制与代码一致。

以下情况只能标记“部分完成”：

- 只有解析器或内存模型。
- 只能打开，不能可靠保存。
- 只有单一手工样本。
- 高级对象会丢失但界面未阻断。
- 尚未接入搜索、最近文件或统一打开。
- 只能在浏览器模拟，未在真实 Tauri 桌面验证。

## 12. 发布门槛

基础版本进入发布候选前应满足：

| 领域 | 最低门槛 |
|---|---|
| 文本与 JSON | TXT/JSON 完整闭环；日志和主要配置格式可读，敏感文件受保护 |
| PDF | 阅读、批注和页面级整理可用，正文编辑边界清晰 |
| 图表与脑图 | Mermaid、Canvas、OPML 和 Table 图表保持可编辑事实源 |
| Office | XLSX 基础编辑稳定；DOCX/PPTX 可读并开放经验证的基础编辑子集 |
| 体系化管理 | 所有已支持格式进入统一打开、最近、搜索、收藏/集合和能力展示 |
| 数据安全 | 外部冲突、写入中断、损坏输入和高风险对象均有阻断或恢复 |
| 兼容声明 | 每种格式公开说明完整编辑、基础编辑、阅读/批注或仅预览 |

## 13. 推荐的连续开发顺序

按以下顺序逐项开发，不跨越未完成的 P0/P1 门禁：

1. `A0` 格式契约与能力展示。
2. `A1` 可靠文本读取与保存内核。
3. `A2` TXT 完整工作面。
4. `A3` JSON/JSONC 工作面。
5. `A4` LOG、YAML、XML、TOML 和配置格式。
6. `A5` 真实桌面验收与阶段审计。
7. `B0～B3` PDF 页面级编辑。
8. `C0～C2` DOCX 只读与基础编辑。
9. `C3～C5` PPTX 只读与基础编辑。
10. `D1～D4` 统一管理闭环补强。
11. `E` WPS、OpenDocument、旧版 Office、SVG、Draw.io 和更多代码格式。
12. `F` 高级等价与 AI 增强。
