### F5 网页收集：按上一轮建议评估纳入

候选范围为“粘贴公开网页链接 → 预览提取结果 → 选择目录 → 保存本地 Markdown”，保留标题、原网址和采集时间，接入收集箱。不是浏览器扩展、登录页面抓取或整站下载。

先验证提取质量、编码、图片/链接处理、网络失败及危险内容净化；不执行远端脚本、不绕过登录或访问限制。失败时保留输入并明确解释，不把残缺页面标为完整收集成功。评估后向用户说明是否纳入本版；不得自行将候选记为已完成或悄悄移除。

来源定位/失效关联、中文搜索响应、窄屏、键盘和减少动效支持作为跨功能质量要求持续改善。云同步、多人协作、完整 Office 等价编辑和大型 AI 系统不在本次确认范围。

## 3. 封板前必须完成 UI 重构

用户要求：**保留现有界面的所有功能；每个界面正式修改之前，先出一张示意图给用户看。**

执行约束：

1. 先读真实界面代码并观察现状，登记全部现有功能、入口、快捷键、菜单、权限和只读/编辑边界、状态提示、保存与恢复行为。
2. 建立“旧功能/入口 → 新位置/操作 → 回归案例”对应表。可优化布局和文案，但不得以简洁为由删除、禁用或藏掉可用功能；罕用功能移入菜单也要保留可发现入口。
3. **每个界面至少先提供一张可视示意图**，标出导航、工具栏、主内容、参考/详情区、状态和关键操作；附调整理由与功能对应表。图片标为“设计示意，非已实现界面”。纯文字方案不替代示意图。
4. **等待用户明确确认该界面的方向后，才允许修改其正式 UI。** 总体风格确认、另一个页面确认或未回复，都不等于当前界面获批。被否决则修订示意图，不能先实现再要求验收。
5. 新增功能的可见界面同样遵循先示意后实现。公共组件或全局样式影响多个页面时，先列明影响范围、提供受影响页面示意，并逐页获得确认；不能用公共样式调整绕过审批。
6. 实现后以真实截图和用户操作复核，不拿示意图当验收证据；每页完成代码审计、功能回归、文档与推送，再进入下一页。
7. 窄窗、深浅主题、高对比、键盘焦点、中文输入、减少动效，以及加载/空白/失败/未保存状态均纳入设计和验证。特效不得妨碍阅读、输入、拖动或缩放。
8. 封板前核对全界面清单与功能对应表：无未确认改版、无遗漏功能、无阻塞性回归。未完成则不能宣称 UI 重构已收口。

## 4. 开发顺序与发布门禁

1. **基线审计**：确认现有代码、功能清单与版本合同；为 1.1.0 规划兼容迁移。产出第一批界面盘点和整体视觉原则，不直接批量改版。
2. **F1 收集箱**：先提交相关页面示意图，确认后实现记录、保存、归档闭环；审计、测试和推送。
3. **F2 工作区**：同样先示意确认，再完成恢复、切换和异常场景；审计、测试和推送。
4. **F3 智能集合**：先示意确认，再完善筛选、持久化与结果刷新；审计、测试和推送。
5. **F4 历史恢复**：先示意确认，再完成差异、副本、草稿保护和复开验证；审计、测试和推送。
6. **F5 决策与其余 UI 页面**：反馈网页收集评估；按逐页审批台账完成余下界面重构。不能把全部 UI 改版压到临近发布时突击完成。
7. **封板与发布**：逐项检查功能保留、跨模块用户场景、性能和视觉；固定候选构建 MSI/NSIS、执行安装及跨小版本升级/回滚验收、公开附件回下载核验。运行包与证据绑定同一提交，不沿用旧包通过结果。

验收使用用户任务，例如“记录会议后归档到项目”“关机后继续昨天写作”“查看项目近期 PDF”“比较修改后恢复为副本”。保留失败和修复复验记录，不为通过测试而修改正确预期。性能先测基线再定目标，不用单一帧率代表全部可用性。

发布说明明确实际验收范围；官方应用内更新观察仍是独立任务，不以覆盖安装替代。README 延续产品介绍优先、末尾简短更新摘要的要求。
