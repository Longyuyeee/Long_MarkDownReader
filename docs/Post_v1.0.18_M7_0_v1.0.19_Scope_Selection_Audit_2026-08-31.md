# v1.0.19 M7-0 范围选择审计

## 1. 接续点与最初需求

v1.0.18 的发布与官方更新链已经全部收口。v1.0.19 必须重新从真实代码和最初专业能力路线选取一个可验证切片，不延续发布测试，也不直接提升版本。最初路线明确提出 JSON/YAML/XML/TOML 的可选 Schema、错误路径定位和结构提示，并要求“未配置 Schema 时不制造错误；配置后错误能定位到路径和源码行列”。

## 2. 实际代码基础

JSON/JSONC 已有 16 MiB 源码上限、20 万节点预算、2 万路径条目、稳定路径与行列、语法/重复键/精度诊断、显式保存和签名冲突保护。`JsonEditorView.vue`、JSON 格式层和命令层中的 `$schema`、`schemaProvider`、`schemaUri` 集成 token 均为 0，因此语法合法但业务类型错误的文档仍显示 0 条业务诊断。

YAML/TOML 虽有相似的有界结构基础，但到 JSON Schema 的标量、标签、多文档和数值投影尚无合同；XML 对应 XSD，还涉及 namespace、import/include 与外部资源阻断。图谱代理折叠、治理环和 ODP 备注的高风险缺口也没有消失。

## 3. 候选比较与选择

唯一选择 **M7-1 本地 JSON Schema sidecar provider/mapping 可行性审计**。选择理由是 JSON Schema 标准与 JSON 实例直接相邻，现有路径和行列可用于诊断定位，同时仓库已有“同目录、同 stem、只读 sidecar”的安全发现先例。

M7-1 只允许 JSON/JSONC 与本地同目录确定性 sidecar；禁止联网、远程 URI 自动解析和静默下载。必须冻结 sidecar 命名、Schema 大小/引用预算、诊断来源、实例路径到源码行列的映射，以及损坏、不支持或不安全 Schema 的降级表现。无 Schema 时必须保持 0 条业务约束诊断，文档和 Schema 均不得被验证过程写入。

## 4. 预期与实际差异

- 不能把四种结构化格式包装成一个“Schema”按钮：它们对应不同标准和安全边界，因此先选择 JSON/JSONC。
- 现有诊断只证明语法，不证明业务约束；后续 UI 必须明确区分“语法有效”和“Schema 验证结果”。
- 远程 provider 看似方便，但与离线、隐私和可复现要求冲突；M7-1 先建立本地显式来源。

## 5. 发布与后续边界

M7-0 不修改产品运行代码，不提升 1.0.18 运行时，不打包、不创建 Tag/Release。当前唯一接续点为 **M7-1 本地 JSON Schema sidecar provider/mapping 可行性审计**；只有真实后端样本和真实 Tauri 证明该边界可靠后，才能决定进入产品实现或重新选择范围。
