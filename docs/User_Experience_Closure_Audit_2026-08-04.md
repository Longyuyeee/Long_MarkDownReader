# LongEdit 用户体验收口审计与验收清单

日期：2026-08-04  
基线：`main` / `3b9855f` / v1.0.3  
来源：v1.0.3 安装版真实资料库与多格式测试反馈  
状态约定：`待处理`、`开发中`、`待复测`、`已验收`。只有用户可理解、安装版可操作且回归检查通过，才能标记为 `已验收`。

## 1. 总体结论

当前版本已经具备较广的格式读取、有限编辑和知识关联能力，但还没有达到用户体验收口状态。主要问题不是单个页面，而是五类共性缺口：

1. 安装态权限、更新策略与运行状态存在明确故障。
2. 页面之间没有稳定保持资料库、标签和文件上下文。
3. 通用工作区壳层在高缩放、小窗口和多标签场景下会挤压或暴露原生滚动条。
4. 文本、结构化数据、表格、Office、图谱等编辑器缺少统一的视觉与交互标准。
5. 多项内部工程概念直接暴露给用户，名称和操作结果难以理解。

因此，本轮不再继续增加零散能力，先按本文顺序完成“可靠性止血 -> 工作区统一 -> 编辑器体验 -> 专业格式 -> 全格式验收”。

## 2. 已确认根因

- `src-tauri/capabilities/default.json` 仅授权 `dialog:allow-open` 和 `dialog:allow-save`，没有授权 `dialog:allow-confirm`。删除索引、删除表格行、关闭脏标签等路径使用 `window.confirm`，与安装态报错完全吻合。
- `TableView.vue` 在挂载时立即要求 `store.libraryPath` 非空，却没有等待配置恢复；从图谱返回后路由重建时可能先执行表格读取，造成“表格路径无效或知识库尚未配置”。
- v1.0.3 Release 明确不发布 `latest.json` 和 `.sig`，但 `tauri.conf.json` 仍配置 Tauri Updater 的 `latest.json` 地址，设置页仍提供原生更新检查，因此当前失败是发布策略与客户端能力不一致，不是用户网络操作错误。
- `WorkspaceTabs.vue` 使用 `overflow-x: auto` 和细原生滚动条，没有滚轮横移；标签最小宽度只有 92px，无法稳定显示六个中文字符和关闭按钮。
- `WorkspaceTabs` 根元素设置 `flex: 1 1 auto`，但它同时被放入多个 CSS Grid 页面中的 `auto` 行，是 TXT/LOG 等页面高度分配异常的重要风险。
- CSV/TSV 的 `TableView.vue` 数据模型已支持 `frozenColumns: number`，UI 却退化成 `freezeFirstColumn: boolean`，所以自由冻结前 N 列不需要重做底层格式。
- CSV 的行号按钮直接执行删除并调用 `window.confirm`；“转换为 Table”立即创建文件并替换当前路由，没有事前解释、目标路径确认或结果入口。
- Markdown 默认模式来自已持久化的 `store.editorMode`，缺少对旧配置和首次启动的“所见即所得”迁移保证。
- 外部修改检测混用了磁盘时间与 `Math.floor(Date.now()/1000)`，并且只比较 `modified > lastKnownModified`，没有用读取签名、写入回执和弹窗去重，容易产生焦点切换误报。
- JSON 树形视图虽然限制为 2,000 个可见节点，但每次折叠仍同步扫描全部分析路径，且 2,000 行一次性进入 DOM，不是真正虚拟列表。
- DOCX 当前是结构化阅读加“基础编辑副本”，不是页面等价的直接编辑器；标题栏已经明确写着“原文件只读”。
- Canvas 使用同步 `ResizeObserver(updateSize)`，未做 `requestAnimationFrame` 合并和尺寸相等短路，符合已观察到的 ResizeObserver 循环风险。

## 4. 开发顺序

### 阶段 A：可靠性止血

处理 UX-02、03、07、11、12、16、19、20、22、23、27、34、39。完成后先发布内部修复构建，使用当前测试库复测，不等待视觉大改一起交付。

### 阶段 B：统一工作区壳层

处理 UX-01、08、09、10、17、18、21、35、36。统一标签、文件树、关系入口、响应式工具栏、确认服务和返回上下文。

### 阶段 C：文本与结构化编辑器

处理 UX-24 至 UX-31。抽出共享 CodeMirror 主题与编辑器壳层，再分别接入 TXT、HTML/代码、JSON、YAML、XML、TOML；LOG 保留专业查看器并增加编辑入口。

### 阶段 D：表格与 Office

处理 UX-13、14、15、32、33。先收口 CSV/TSV 和工作簿交互，再调整 DOCX 阅读与编辑路线。

### 阶段 E：图谱、脑图与全格式验收

处理 UX-05、06、37、38。术语、主题库和图形编辑一起收口，最后按格式矩阵逐项验收。

## 5. 每步必做审计

1. 代码审计：记录变更文件、根因和兼容边界。
2. 自动检查：至少执行 TypeScript/Vite 构建、相关前端检查和受影响 Rust 测试。
3. 安装态检查：不能只看浏览器开发态；必须验证 Tauri 安装版 ACL、资源、路由和主题。
4. 视觉检查：100%、150%、200% 缩放；至少 1366x768、1920x1080 和窄窗口。
5. 真实文件检查：使用 `E:\Long\Long编辑测试库-v1.0.3`，保存结果放到其 `99-保存输出到这里`，不覆盖原始样本。
6. 文档回写：只在验收条件满足后更新本文状态，并记录提交号和复测结果。

## 6. 已确认的产品决策

1. DOCX 目标为直接编辑源文件的页面式编辑器；编辑期间不自动写盘，只有用户点击保存才写回源文件。
2. LOG 保留专业日志查看器，同时提供编辑模式；允许用户明确确认后保存并覆盖原 `.log`。
3. HTML 默认进入源码编辑，同时提供隔离危险能力的安全网页预览模式。
4. 所有可编辑格式统一提供返回、撤销和重做按钮；所有格式都遵循“编辑停留在内存，点击保存才写入文件”的交互原则。

上述范围已经确认，没有遗留的产品决策阻塞，可直接按阶段 A 开始开发。
