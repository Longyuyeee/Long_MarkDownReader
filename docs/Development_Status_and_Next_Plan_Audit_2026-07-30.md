# LongEdit 当前开发情况与后续计划综合审计

> 审计日期：2026-07-30
>
> 审计输入基线：`a1114a3`（`main`，审计开始时与 `origin/main` 一致）
>
> 产品版本：`v0.7.0`
>
> 审计范围：统一文件管理、日常格式阅读与基础编辑、PDF、图表、思维导图、知识图谱、WPS/Office/OpenDocument、TXT/JSON/开发格式、可靠保存与发布门禁
>
> 结论性质：产品与工程综合审计；不以“能打开”替代“能编辑”，不以内部实现替代真实生产者验证

## 1. 审计结论

LongEdit 已经从 Markdown 阅读器发展为一个**可实际使用的本地多格式资料管理工作台**。统一文件树、右侧工作面、全文搜索、最近与收藏、标签、索引、批注、引用、知识关系、Canvas、思维导图、图表和多种专业格式工作面已经形成主干闭环。

但相对于最初目标：

> **覆盖用户日常使用中的文件管理和基础编辑，并把分散文件组织成一套可持续使用、可查找、可关联、可维护的管理体系。**

当前应判定为“**核心能力基本形成，格式长尾与专业发布边界仍需收口**”，不能宣称所有初始需求 100% 完成。

主要判断如下：

1. **日常管理闭环：基本完成。** 文件发现、识别、阅读、搜索、定位、分类、最近/收藏、关系与索引已经统一到产品主界面。
2. **文本与开发格式：达到基础目标。** Markdown、TXT、JSON/JSONC、YAML、XML、TOML、配置文件及常见代码格式已进入统一编辑工作面。
3. **图表与思维导图：核心闭环完成。** Table 图表、Mermaid、JSON Canvas 和 OPML 均可在软件内编辑；Canvas 已具备专业思维导图所需的布局、折叠、关系、复制和大画布能力。
4. **知识图谱：已从“展示功能”进入管理主干，但存在感仍可增强。** 全局/局部图谱、筛选、治理、跨格式节点和图谱转 Canvas 已完成；关系类型可视化编辑、证据展开和面向日常任务的上下文入口仍不完整。
5. **PDF：阅读研究与页面管理较强，正文级编辑未实现。** 阅读、文本层、搜索、批注、引用、OCR 接口、大文件范围读取、页面提取/合并/插入已完成；这不等同于 Acrobat 类正文、表单、签名或版面编辑。
6. **Office：现代格式已达到“基础编辑”，尚未达到完整 Office 等价。** DOCX、PPTX、XLSX 有结构化工作面和可靠新副本边界；高级排版、复杂对象、外部链接、动态数组写回等仍受限。
7. **WPS/旧版 Office/OpenDocument：是当前最影响初始需求完整度的缺口。** `.wps/.et/.dps`、`.doc/.xls/.ppt` 尚未进入正式支持注册表；ODT 只读实现完成但 WPS 生产者门禁仍为 2/3，因此 `.odt` 尚未发布登记；`.ods/.odp` 尚待实施。

因此，下一阶段不应继续把大部分资源投入单一 XLSX 高级特性。应优先完成“常见格式能识别、能在右侧阅读、能明确降级到外部应用或安全转换”的基础覆盖，再继续 Office 深度与知识图谱增强。

## 2. 审计方法与证据

本次结论来自以下可复核来源：

- `shared/file-formats.json`：统一格式注册表和用户能力等级；
- `shared/office-compatibility-audit.json`、`shared/odf-package-contract.json`、`shared/odt-read-contract.json`：Office/WPS/ODF 边界；
- `shared/xlsx-compatibility-matrix.json`、`shared/xlsx-formula-capabilities.json`、`shared/xlsx-linked-data-capabilities.json`、`shared/xlsx-release-gate.json`：XLSX 能力与发布门禁；
- `docs/Product_Requirements_and_Development_Roadmap.md`：FR 状态和阶段验收记录；
- PDF、DOCX、PPTX、XLSX、图谱、格式合同及真实桌面证据检查脚本；
- 审计开始时的 Git 状态、远端同步状态和现有完整 CI。

能力等级必须按以下口径解释：

| 层级 | 含义 |
| --- | --- |
| 可识别 | 文件能被准确路由，并显示真实能力与降级说明 |
| 可阅读 | 软件内能形成有意义的内容预览、搜索或定位 |
| 可基础编辑 | 能修改约定范围内的内容，但不代表完整复刻原生软件 |
| 可可靠保存 | 通过事务、新副本、重开和必要生产者矩阵验证 |
| 完整编辑 | 对该开放格式的目标编辑范围形成读写闭环；仍不等于支持格式规范的每个扩展特性 |

## 3. 机器可读格式基线

`shared/file-formats.json` 当前登记 **31 类格式**：

| 指标 | 当前结果 |
| --- | ---: |
| 可读取 | 31 / 31 |
| 编辑标记为 supported | 29 / 31 |
| 完整编辑等级 | 13 |
| 基础编辑等级 | 16 |
| 阅读/批注等级 | 1（PDF） |
| 仅预览等级 | 1（LOG） |
| 可创建 | 16 |

这里的“29 类可编辑”包含代码文本和受边界保护的 Office 基础编辑，不能解释为 29 种格式均达到原生应用等价。注册表目前也尚未包含 WPS 原生格式、旧版 Office 和 OpenDocument，因此 31/31 只代表**已登记格式内部的读取覆盖**，不是用户日常格式全集的完成率。

## 4. 按原始需求审计

### 4.1 日常文件管理与体系化组织

状态：**基本完成，可用。**

已形成的主链路：

```text
发现/识别 → 右侧工作面阅读 → 编辑或批注 → 安全保存/新副本
    → 搜索与再次定位 → 标签/集合/引用/关系 → 知识健康治理
```

已完成：

- 统一文件树、能力标签和最长扩展名路由；
- 右侧工作面承载 Markdown、文本、开发格式、PDF、Office、表格、Canvas、OPML 和 Mermaid，未把新增格式割裂成另一套主界面；
- 最近文件、收藏、搜索、索引、对象定位和外部打开；
- 文件、标题、PDF 批注、Canvas、OPML、表格与图表进入统一关系网络；
- 断链、歧义、孤立内容、重复文件、未处理批注和索引状态治理；
- 保存边界、冲突提示、原件保护和可靠新副本策略。

待收口：

- 未支持格式的“在右侧识别 + 能力说明 + 外部打开/显式转换”还没有覆盖 WPS 原生、旧版 Office 和全部 ODF；
- 跨格式对象的统一操作菜单、批量归档和关系创建入口仍可进一步统一；
- 发布版安装、文件关联、迁移、恢复和用户帮助尚需最终验收。

### 4.2 TXT、JSON 与开发常用格式

状态：**基础目标完成。**

- Markdown、TXT、INI/CONF/CFG、Properties、EditorConfig、GitIgnore、YAML、XML、TOML 已达到完整编辑等级；
- JSON/JSONC 已支持结构化编辑、校验、格式化、搜索、创建和可靠保存；
- JavaScript/TypeScript、Python、Rust、Go、Java/Kotlin、C 系、Shell、SQL、HTML/CSS/Vue 等已支持基础代码编辑与搜索；
- `.env` 明确采用敏感信息保护边界，不进入普通全文索引；
- LOG 当前保持只读预览，避免把日志查看器虚假描述为编辑器。

后续只需补齐创建模板、超大文本性能和编码/换行兼容，不应再作为阻塞初始需求的主线。

### 4.3 图表、流程图与思维导图

状态：**核心目标完成，富媒体节点待增强。**

- CSV/TSV/Open Table 可编辑，并可切换表格、看板和图表视图；
- 图表编辑器已覆盖柱、线、饼、散点、字段映射、聚合、空值策略和本地 SVG；
- Mermaid 已覆盖源码编辑、实时预览、错误定位、常用结构表单、SVG/PNG 导出和 Canvas 引用；
- JSON Canvas 已覆盖标准读写、拖拽缩放、连线分组、多选、撤销重做、吸附、边属性、分支折叠、自动布局、复制粘贴和千节点优化；
- OPML 已形成专业层级编辑与思维导图导入/导出通道。

主要缺口是 `FR-CANVAS-010`：图片、PDF 批注和数据图表节点的原位预览尚未完成。用户虽然已经可以“做思维导图”，但跨格式资料进入思维导图后的信息密度和直观性仍有提升空间。

### 4.4 知识图谱的存在感

状态：**核心完成，产品入口与关系创作仍需强化。**

已完成：

- 全局关系网络与思维导图双模式；
- 编辑器内 1～3 跳局部图谱；
- 图谱一键生成标准 `.canvas`；
- 标签、目录、日期、类型统一筛选；
- 断链、歧义链接和孤立笔记治理；
- 布局持久化与 PNG/SVG 导出；
- PDF 批注、Canvas、OPML、表格、图表等跨格式对象关系。

仍需完成：

- `FR-GRAPH-004` 从“部分完成”提升为完成：关系类型可视化编辑、全部证据展开、来源上下文定位和跨格式关系证据一致化；
- 在右侧文件工作面提供稳定的“相关内容 / 为什么相关 / 添加关系”区域，而不是要求用户主动进入图谱页；
- 在搜索结果、最近文件、PDF 批注、Office 对象和工作台任务中显示轻量关系线索；
- 提供“以当前文件生成思维导图”“把选中对象加入现有 Canvas”等直接动作；
- 增加基于图谱的收件箱、未归类内容和项目上下文视图，让图谱参与日常整理，而不只是可视化。

增强方向应遵循“图谱服务文件管理”的原则，不建立一套与文件工作面割裂的新导航系统。

### 4.5 PDF

状态：**阅读、研究与页面管理闭环；正文级编辑未完成。**

已完成：

- 内置阅读、缩略图、目录、阅读位置；
- 文本层、复制、全文搜索、命中定位；
- sidecar 高亮、区域和评论批注；
- Markdown 引用与精确返回；
- PDF 内容与批注进入统一搜索和知识图谱；
- OCR provider 接口与任务状态；
- 大文件渐进范围读取；
- 页面提取、PDF 合并、页面插入及真实桌面证据。

未完成：

- PDF 正文、字体和复杂版面直接改写；
- AcroForm 表单填写与可靠新副本；
- 数字签名、可信验证、永久脱敏和高级审阅流程。

产品应继续标记为 `read-annotate`，页面操作属于安全的新副本管理能力，不得改写为“PDF 完整编辑”。

### 4.6 DOCX、PPTX 与 XLSX

状态：**现代 Office 基础编辑可用；完整兼容专项未完成。**

DOCX 已完成结构化阅读、搜索定位、知识关系、基础文本/样式编辑和可靠新副本；复杂分页、域、修订、脚注尾注、浮动布局及宏等不在当前完整支持范围。

PPTX 已完成结构化阅读、搜索定位、关系、文本/样式/替代文本、图片替换、形状和幻灯片生命周期以及三生产者复开；母版、动画、SmartArt、复杂图表和宏仍不是完整编辑能力。

XLSX 已形成多 Sheet 阅读、基础单元格编辑、公式与对象审计、表格/图表工作面、可靠新副本和大量真实生产者矩阵。当前高级边界包括：

- 数组/动态数组只读诊断已完成，真实生产者矩阵仍为 `partial 1/3`；
- 当前机器只验证 WPS Spreadsheets；真实 Microsoft Excel 和 LibreOffice Calc 证据待外部机器导入；
- 数组计算、spill 结果生成和数组写回继续阻断；
- 外部工作簿引用的读取清单、离线/断链诊断和定位是下一个本地可开发入口；
- 不开放原件覆盖，不宣称完整 Excel 等价。

### 4.7 WPS、旧版 Office 与 OpenDocument

状态：**审计与安全边界已建立，面向用户的格式覆盖未完成。**

- ODF 包安全检查、ODT 解析、右侧只读工作面、搜索和定位已经实现；
- Word 与 LibreOffice ODT 生产者证据通过，当前 WPS 环境输出 OLE 而非可信 ODT ZIP，E1B 保持 2/3，`.odt` 尚未登记；
- `.ods/.odp` 的只读结构预览与生产者矩阵尚待 E1C；
- 外部应用发现与统一外部打开尚待 E2A；
- `.doc`、`.xls`、`.ppt` 的显式隔离转换尚待 E2B/E2C；
- `.wps`、`.et`、`.dps` 的真实 fixture、识别、外部打开和转换资格尚待 E3。

这是下一阶段最应优先解决的格式覆盖问题。短期目标不是自行复刻 WPS，而是让用户在 LongEdit 中看到文件、知道能力边界、可安全调用本机应用，并在明确确认后转换为可管理的新格式副本。

## 6. 风险与偏差审计

### 6.1 路线偏差

近期 XLSX 高级兼容投入形成了严谨的生产者证据体系，但继续无限深入 Pivot、数组与完整公式等价，会降低用户最初所要求的日常格式覆盖速度。后续每个 Excel 专项必须证明它比 WPS/旧 Office/ODF 基础覆盖更高优先，否则不得占用 P0/P1 主线。

### 6.2 能力口径风险

格式注册表中 `edit: supported` 代表产品允许约定范围内编辑，不代表完整原生兼容。界面、文档和发布说明必须同步显示 `complete-edit`、`basic-edit`、`read-annotate`、`preview-only` 及保存模式。

### 6.3 外部环境风险

WPS ODT、Excel/LibreOffice 数组矩阵依赖真实外部生产者。缺少环境不是降低门禁的理由。项目已经具备跨机器证据交接和原子导入能力，应等待可信证据，不应生成伪造 fixture。

### 6.4 界面一致性风险

新增格式必须继续打开在既有主窗口右侧工作面，并复用原有字号、间距、色彩、标题栏和响应式布局。除明确的系统对话框或外部应用外，不新增割裂的第二套主界面。

### 6.5 文档漂移风险

现有执行指南保留了大量历史阶段入口，容易让接手者误把旧“下一步”当成当前入口。本审计之后，恢复开发必须先看本文件第 7 节；旧阶段文字只作追溯证据。

## 7. 后续开发计划

### 阶段 F1：日常格式覆盖收口（最高优先级）

目标：先让 WPS、旧版 Office 和 ODF 文件进入统一管理闭环，即使部分格式暂时只能预览、外部打开或显式转换。

执行顺序：

1. **E2A 外部应用能力发现与统一外部打开**
   - 识别 WPS、Microsoft Office、LibreOffice 的真实可执行程序与版本；
   - 所有入口复用右侧工作面能力说明；
   - 外部打开失败可诊断，不修改源文件。
2. **E3 WPS 原生格式识别**
   - 固定 `.wps/.et/.dps` 真实 fixture 与隐私清理规则；
   - 先实现识别、元数据、能力提示和外部打开；
   - 转换资格单独验收，不把外部打开描述为内置编辑。
3. **E2B/E2C 旧版 Office**
   - `.doc` 先行，再到 `.xls/.ppt`；
   - 只允许用户显式触发的隔离转换；
   - 生成新副本，保留原件，记录转换器、版本和失真提示。
4. **E1C OpenDocument**
   - 实现 `.ods/.odp` 只读结构预览、搜索、定位和真实生产者矩阵；
   - E1B 的 WPS ODT 证据作为外部并行门禁，证据到位后原子登记 `.odt`。

退出条件：

- 上述扩展名都能在文件树中被正确识别；
- 双击后进入右侧能力工作面或受控外部打开，不出现无解释失败；
- 每个格式明确声明读取、编辑、创建、索引与保存等级；
- 转换始终生成新副本，失败不污染原件。

### 阶段 F2：PDF 与富媒体节点

目标：补齐最常见的“基础编辑”场景，并让 PDF/图表真正进入思维导图。

执行顺序：

1. 实现 AcroForm 字段读取、基础填写、校验和可靠新副本；
2. 完成 `FR-CANVAS-010`：图片、PDF 批注和数据图表节点原位预览；
3. 增加从 PDF 选区/批注、表格图表直接加入当前 Canvas 的动作；
4. 数字签名和永久脱敏只做审计，不在缺少密码学与不可逆操作门禁时开放。

退出条件：表单新副本可由主流 PDF 阅读器复开，Canvas 富媒体节点可定位回源对象，删除/移动源对象有明确断链状态。

### 阶段 F3：知识图谱存在感与思维导图工作流

目标：让关系在用户阅读、整理和回访文件时持续可见，而不是只在图谱页面出现。

执行顺序：

1. 完成 `FR-GRAPH-004` 的关系类型可视化编辑与全部证据定位；

## 9. 每步开发的强制审计模板

后续每个阶段都必须同时回答：

1. 本步直接改善了哪个用户任务？
2. 新格式现在是可识别、可阅读、可编辑还是可可靠保存？
3. 是否仍在原有主窗口右侧工作面，视觉是否复用现有设计系统？
4. 源文件失败时是否保持不变，是否生成可追踪的新副本？
5. 搜索、索引、定位、关系与知识图谱是否同步接入？
6. 真实生产者和桌面证据是否满足，未满足时是否如实阻断？
7. 文档、机器合同、测试、提交和远端分支是否同步？

只有功能、证据、文档和 Git 远端四者一致，阶段才允许标记完成。

## 10. 本次审计后的产品定位

LongEdit 当前最准确的定位是：

> **一个以本地文件为事实源、覆盖常用文本与开发格式并具备 PDF 研究、现代 Office 基础编辑、图表、思维导图和知识关系能力的多格式资料管理工作台。**

它已经明显超过 Markdown 阅读器，但还不是完整的 WPS/Office/PDF 替代品。接下来应以“补齐日常格式覆盖、让关系服务当前文件、完成专业发布闭环”为主线，而不是继续以单一高级格式的功能数量衡量进度。

## 11. CI 绿色基线恢复

综合审计提交后的远端 Quality Gate 暴露出 PowerShell Runner 兼容问题：S8-7E3G、X3-B5、X3-B6 新证据脚本依赖 `Get-FileHash`，GitHub Runner 无法识别该命令。现已统一改为自包含的 .NET SHA-256 helper，并由机器契约阻止相关脚本回退。

本地三条证据事务测试和完整 `ci:check` 已通过，Rust 功能测试为 `383 passed`，性能测试 `1 passed`，生产依赖漏洞为 `0`。该修复不改变 Pivot 或数组公式公开能力；下一代码入口仍为 F1/E2A。详细记录见 [`CI_PowerShell_SHA256_Portability_Audit_2026-07-30.md`](./CI_PowerShell_SHA256_Portability_Audit_2026-07-30.md)。

首次远端复验已越过哈希故障，随后确认 GitHub 父 `pwsh` 与子 `powershell.exe` 的临时目录环境不同。现已增加统一路径安全 helper，在不放宽审计写入边界的前提下支持 `RUNNER_TEMP`，并通过跨环境边界、前缀逃逸拒绝、X3-B5 与 X3-B6 针对性验证。产品能力和下一阶段顺序保持不变。
