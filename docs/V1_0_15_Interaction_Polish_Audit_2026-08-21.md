# v1.0.15 交互细节治理与桌面验收审计

审计日期：2026-08-21；扩展复核：2026-08-22

开发分支：`codex/v1.0.15-interaction-polish`

当前软件事实版本：`1.0.15`

本轮定位：v1.0.15 候选范围中的交互治理增量；交互验收通过后已统一提升版本并进入无签名社区版发布流程。

## 1. 结论

用户指出的交互问题已经完成代码修复、静态门禁、生产构建与真实 Tauri 桌面验收：

1. 顶部文档标签不再使用浏览器原生 `title` 提示，改为软件内统一提示层，显示文件名、完整路径和未保存状态。
2. 普通软件区域右键不再弹出 WebView 默认的“粘贴、全选、更多工具”等菜单；输入框、文本域、CodeMirror、Vditor 等真实文本编辑区域仍保留原生文字操作；文件树等已有专用右键菜单不受影响。
3. PDF、文档、图表、知识图谱与资料库等工作区遗留的原生 `title` 已由运行时统一接管为主题化软件提示层；动态生成元素同样受控，并补齐键盘焦点、ARIA、Escape 关闭和视口边界。
4. 资料库“新建”菜单随格式增长形成的超长列表已改为视口内滚动浮层，并修正侧栏层级、淡入验收时序和亮/暗主题窄屏表现。

扩展审计同时发现大量原生 `window.confirm`、`window.alert`、`window.prompt` 会破坏桌面产品的一致性。本轮已全部迁移到 Naive UI 应用内确认框和参数输入框，仓库扫描结果三项均为 0。

本轮没有改变最初产品目标和工作区结构：启动后仍是左侧资料库/功能入口、顶部标签、右侧阅读编辑区及右侧检查器；没有新建另一套编辑页面或外部窗口。

## 3. 审计过程中发现并纠正的问题

首次验收脚本的 Vite 端口与 `tauri.e2e.conf.json` 不一致，窗口没有加载应用；已统一为 14200。第二次验收确认提示层实际能够出现，但发现脚本错误假设首个标签必然是最先打开的文件；已改为匹配真实悬停标签。

更重要的是，真实截图暴露出静态合同未发现的视觉问题：内容区域虽已使用主题白色，Naive UI Tooltip 外壳仍保留默认深色背景，形成粗黑边。该问题随后改为通过组件主题覆盖统一整个提示表面，重新采集的桌面截图已人工接受。

扩展抽样又发现“新建”菜单包含约 30 个入口时会穿过侧栏底部。菜单增加滚动与视口约束后，第一次几何门禁虽然通过，但人工截图仍捕捉到淡入过程中的半透明帧；最终验收增加了浮层层级、父层透明度和动画稳定等待，避免把过渡帧误当成最终视觉。DPR 浮点容差与 Windows CRLF 检出差异也已在门禁中统一。

## 4. 需求对齐

本轮服务于最初的基础需求，而不是扩张产品边界：

- 日常管理：文件树、自定义菜单、标签切换和路径识别保持在同一资料库工作流。
- 基础阅读与编辑：文本编辑区域仍保留必要的复制、粘贴、全选等上下文能力。
- 成体系管理：普通壳层不再暴露浏览器/WebView 工具菜单，交互语义更接近专业桌面管理软件。
- 统一 UI：提示、确认和参数输入回到现有主题与组件体系，没有引入第二套页面风格。

全格式能力边界没有在本轮改变：现有格式仍按直接编辑、有界可靠副本、预览、外部依赖四类事实运行，不应把“可打开”宣传成任意内容的完整 Office/PDF 原位编辑。
